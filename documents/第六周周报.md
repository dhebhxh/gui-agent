## 二、测试第一次微调效果，并完成第二次微调

### 2.1 第一次微调结果与问题发现

完成第一次模型微调后，对模型的 GUI 元素定位能力进行了测试，发现模型存在明显的坐标定位失准问题，预测的动作坐标与目标 UI 元素的实际位置存在较大偏差。

经过排查，发现问题出现在 Mind2Web 训练数据的预处理阶段：使用 Qwen 的 `smart_resize` 方法对原始截图进行了缩放，但没有同步调整对应的坐标标注。

这导致训练数据中的图片与坐标标签使用了不同的尺寸基准。模型虽然接收到缩放后的截图，但监督信号仍然对应原始图片的坐标系，最终影响了模型的坐标定位能力。

### 2.2 数据预处理流程修正

Mind2Web 数据集包含大量高分辨率长截图。如果直接使用原始图片进行微调，会产生较大的 GPU 显存开销。因此，仍然需要保留 Smart Resize，而不是直接取消图片缩放。

针对第一次微调暴露的问题，我重新调整了数据预处理流程，确保图片尺寸与动作坐标始终保持一致。

获得原始图片和目标UI元素中心点后，使用 qwen_vl_utils 库中的 `smart_resize` 方法，根据原始图片的宽高及预设像素约束，计算缩放后的目标尺寸。

核心代码如下：

```python
import cv2
from qwen_vl_utils.vision_process import smart_resize

# 1. 读取原图
image = cv2.imread("screen.png")
original_h, original_w = image.shape[:2]

# 2. 使用 smart_resize 获取目标尺寸
resized_h, resized_w = smart_resize(
    original_h,
    original_w,
    factor=28,
    min_pixels=4 * 28 * 28,
    max_pixels=16384 * 28 * 28
)

# 3. 计算缩放比例
scale_x = resized_w / original_w
scale_y = resized_h / original_h

# 4. 缩放原图
resized_image = cv2.resize(
    image,
    (resized_w, resized_h)
)

# 5. 原始坐标
original_bbox = [100, 200, 500, 600]  # x1, y1, x2, y2

# 6. 同步缩放坐标
resized_bbox = [
    round(original_bbox[0] * scale_x),
    round(original_bbox[1] * scale_y),
    round(original_bbox[2] * scale_x),
    round(original_bbox[3] * scale_y)
]

print("Original size:", (original_w, original_h))
print("Resized size:", (resized_w, resized_h))
print("Scale:", (scale_x, scale_y))
print("Resized bbox:", resized_bbox)

```

### 2.3 第二次微调结果

完成上述数据预处理流程的修正后，重新生成训练数据并进行了第二次模型微调。

测试结果显示，模型的坐标定位能力恢复正常，能够比较准确地定位目标 UI 元素。这证明第一次微调中的坐标偏差确实与图片缩放和坐标标注不一致的问题有关。

同时，推理阶段也采用与训练阶段一致的图片缩放策略，确保模型输入与坐标输出保持一致的尺度关系。


## 三、将 print 替换为 Python logging

学习并使用 Python 标准库 `logging` 重构项目日志系统，掌握 `Logger`、`Handler`、`Formatter` 等核心组件的使用方式，以及核心数据类 `LogRecord` 的作用、日志传播（Propagation）机制和日志级别的使用规范。

将原有的 `print` 调试输出统一替换为结构化日志，并按照 Agent 的执行流程重新组织日志内容，主要包括：

### 1. 统一日志格式

- 为每条日志添加时间戳、日志级别和模块名称（Logger Name），明确标注日志来源，例如 `agent`、`perception`、`verifier`、`planner` 和 `executor`。
- 根据日志重要程度区分 `INFO`、`DEBUG`、`WARNING` 和 `ERROR` 等级，兼顾日常运行信息与详细调试信息。
- 通过统一的 Formatter 规范日志输出格式，提高日志的可读性和可追踪性。

### 2. 完善各节点内部日志

针对不同节点的职责，补充关键状态变化和执行过程日志：

- **Agent：**
  - 记录 Agent 创建成功及使用的模型、API 地址、最大执行步数等配置信息。
  - 记录任务开始、结束及当前执行步数。
  - 记录每轮 Agent 循环的执行耗时。

- **Perception：**
  - 记录截图请求及响应状态、耗时和数据大小。
  - 记录截图解码结果、原始截图保存路径。
  - 记录图像缩放前后的分辨率，以及 `scale_x`、`scale_y` 坐标缩放比例。
  - 记录节点整体执行耗时。

- **Planner：**
  - 记录大模型调用开始和结束，以及单次调用耗时。
  - 保存每一步发送给大模型的完整输入 Prompt 和返回结果。
  - 单独突出显示核心决策结果，包括 `thought`、`expected_result` 和 `action`，便于检查模型的决策逻辑。

- **Verifier：**
  - 记录每次验证的执行状态及验证结果。
  - 输出图像差分分析信息，包括全局变化比例、平均差异值和变化区域等。
  - 记录验证跳过或异常的具体原因。

- **Executor：**
  - 记录当前执行的动作类型及原始坐标。
  - 记录坐标转换前后的结果，便于排查图像缩放导致的坐标定位偏差。
  - 记录动作执行请求、服务器响应状态及执行耗时。

### 实现效果

通过 Python logging 建立了覆盖 Agent 全生命周期的日志追踪机制，实现了从截图获取、图像预处理、模型决策、动作执行到结果验证的完整可观测链路。

在后续测试中，该日志系统帮助快速定位了坐标映射偏差、单击与双击动作选择，以及 Verifier 对截图变化的判断等问题，为后续 Agent 调试、错误分析和架构优化提供了可靠依据。

## 四、新增 Verifier 节点

### 4.1 问题分析与设计思路

在实际测试中，发现 Agent 存在两类频繁问题：

1. **错误动作重复执行**：模型执行的动作没有产生预期效果，但没有及时意识到执行失败，导致重复执行相同动作。
2. **成功动作重复执行**：动作已经成功，但模型未能正确识别执行结果，继续重复执行，影响任务效率。

最初尝试通过修改 Prompt 来改善模型的判断能力，虽然有一定效果，但稳定性不足，同一任务在不同测试中仍可能出现不同的执行结果。

根据导师的建议，决定引入基于前后截图差分的轻量级 Verifier，通过比较动作执行前后的屏幕变化，为模型提供额外的执行反馈，辅助判断上一步动作是否真正产生了效果。

### 4.2 Verifier 节点的设计与实现

在原有 LangGraph 工作流中新增 Verifier 节点，将 Graph 调整为：

`Perception → Verifier → Planner → Executor → Perception`

其中，Verifier 位于 Perception 和 Planner 之间。Executor 执行动作后重新进入 Perception，获取最新截图和屏幕元素信息，再由 Verifier 对比当前截图与上一步执行前保存的截图。

Verifier 的主要输入包括：

- **old_resized_screenshot**：动作执行前的截图。
- **screenshot**：动作执行后的截图。
- **last_action**：上一步执行的动作及其坐标信息。
- **old_elements**：动作执行前识别到的屏幕元素，用于辅助定位点击区域。

Verifier 将检测结果写入 AgentState 的 last_verification_result 字段，供后续 Planner 使用。该字段包含验证状态（status）和原因说明（reason），部分操作还会附带局部及全屏变化比例、变化区域等信息。

### 4.3 基于截图差分的动作验证

具体验证逻辑封装在 ActionVerifier 中，针对不同动作设计了相应的检测方式：

- **单击操作**：根据点击坐标和旧截图中的屏幕元素定位局部区域（ROI），比较该区域及整个屏幕的变化。
- **右键单击**：同时检测点击区域和全屏变化，并记录发生变化的区域。
- **双击操作**：主要检测全屏变化，判断是否出现明显的界面变化。
- **拖拽操作**：分别比较拖拽起点、终点附近的局部区域，并结合全屏变化判断操作效果。
- **文本输入**：提取输入位置附近的区域，比较输入前后的视觉变化。

图像比较通过计算前后截图的像素差异，得到变化比例（changed_ratio）和平均差异值（mean_diff）。

以单击操作为例，当局部区域变化比例超过 2%，或者全屏变化比例超过 1% 时，判定为 `success`；否则返回 `failure`。

需要注意，截图变化只能作为动作是否生效的视觉证据，并不直接代表任务目标已经完成。因此，验证结果主要用于辅助模型判断，而不是代替模型进行任务级判断。

### 4.4 模型反馈

Planner 在下一轮决策时结合验证结果和当前屏幕信息调整行动策略：

- 如果验证成功，避免重复执行已经产生效果的动作，继续推进任务。
- 如果验证结果不确定，重新检查当前界面，判断是否需要调整动作或重新尝试。
- 如果发现上一步操作没有达到预期效果，应避免盲目重复相同动作，必要时重新规划。

通过这种方式，Verifier 为原有 Agent 增加了一层轻量级的执行反馈机制，使模型不再仅依赖自身对动作结果的推测，而是能够结合实际屏幕变化进行判断。

## 五、Verifier 节点效果验证

为了验证新增 Verifier 节点的实际效果，使用相同任务 `open the web browser` 进行对比测试，重点观察模型在动作未产生预期效果时，能否及时调整后续操作。

### 5.1 未能有效利用验证反馈的测试

在改进前的测试中，模型执行单击后，虽然意识到浏览器可能没有打开，但仍然选择再次单击 Firefox 图标，没有尝试改变操作方式。

日志中的模型 Thought 如下：

```text
The goal is to open the web browser. The previous action involved clicking on the Firefox.exe icon, but the verification result indicated no significant visual changes, suggesting that the browser did not open. The Firefox icon is still visible on the desktop, indicating that the browser might not have opened yet. I will attempt to click on the Firefox icon again to ensure the browser launches.
```

从这段日志可以看出，模型已经注意到前后界面没有明显变化，也意识到浏览器可能没有成功打开，但最终仍然选择重复单击。这说明仅依赖模型自身的推理，未必能够将失败判断有效转化为动作策略调整。

### 5.2 加入 Verifier

加入 Verifier 后，重新执行相同任务。以下为 2026-11-25 03:26 这次运行中的关键日志。

**（1）首次单击及验证失败**

```text
2026-11-25 03:26:10 | INFO | planner | planner done | step=0 action=ActionType.LEFT_SINGLE_CLICK

2026-11-25 03:26:14 | INFO | verifier | verification result | status=failure reason=No significant visual changes detected. Local changed ratio: 0.0000, Global changed ratio: 0.0000
```

Verifier 检测到局部和全屏变化比例均为 `0.0000`，说明单击前后没有检测到明显的视觉变化，因此返回 `failure`。

**（2）Planner 根据验证结果调整动作**

```text
"thought": "The previous action involved a left_single_click on the Firefox icon, but the verification result indicated a failure. This suggests that the single click did not open the browser. Since the Firefox icon is clearly visible, I will attempt a left_double_click to open the browser."

2026-11-25 03:26:17 | INFO | planner | planner done | step=1 action=ActionType.LEFT_DOUBLE_CLICK
```

可以看到，Planner 明确引用了上一步的验证失败结果，并将操作从 `LEFT_SINGLE_CLICK` 调整为 `LEFT_DOUBLE_CLICK`，而不是重复原来的单击。

**（3）双击后的验证成功及任务结束**

```text
2026-11-25 03:26:20 | INFO | verifier | verification result | status=success reason={
    'reason': 'Significant visual changes detected after double-click',
    'global_changed_ratio': 0.9011594408630883,
    'global_mean_diff': 70.59745127592772,
    ...
}

"thought": "The previous action was a left_double_click on the Firefox icon, which resulted in a successful verification. The current screenshot shows the Firefox browser window open, indicating that the web browser has been successfully opened."

2026-11-25 03:26:22 | INFO | planner | planner done | step=2 action=ActionType.FINISH
```

双击后，全屏变化比例达到 `0.9012`，平均像素差异为 `70.5975`，表明前后截图发生了大范围视觉变化。Planner 随后结合验证结果和最新截图，确认 Firefox 浏览器已经打开，并输出 `FINISH`，任务成功结束。

### 5.3 对比结果与分析

从两次测试的日志可以看出，主要区别在于模型面对动作失败时的后续决策：

- **改进前：** 模型虽然意识到界面没有明显变化，但仍然选择重复单击。
- **加入 Verifier 后：** Verifier 将截图差分结果反馈给 Planner，模型据此将单击调整为双击，并在检测到明显视觉变化后结束任务。

这表明，独立的 Verifier 节点为 Agent 提供了额外的视觉反馈，使模型能够更明确地判断动作执行结果，并将验证信息用于后续策略调整。

此外，在多次重复测试中，加入 Verifier 后的 Agent 均呈现出相同的三步执行流程，说明该机制在当前测试任务中具有较好的稳定性和可重复性。

需要说明的是，目前验证仍集中在打开浏览器这一任务上，其在其他任务和不同界面环境下的泛化能力还有待进一步测试。
